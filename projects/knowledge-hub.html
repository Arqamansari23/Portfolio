Islamic Knowledge Hub: A Self-Hosted Multi-Agent RAG With Per-Category Judge Loops

A local, self-hosted system that answers users' Islamic questions strictly from a curated corpus of Islamic books — six specialized category agents orchestrated with LangGraph, each fed by its own retrieval lane and its own LLM judge loop, with every answer carrying a book and category citation. No external API: a 14B model, quantised and served on one GPU.

The Problem

Religious questions are exactly where a model must not improvise

People ask religious questions the way they ask any other question — in one sentence, often mixing several distinct information needs, and usually in Urdu. But the tolerance for an invented answer here is zero. An answer is only useful if it can point at the book it came from.

The system was built in-house as a local, self-hosted assistant over a curated corpus of Islamic books. Three constraints shaped every decision:

  • Grounding above all. Every sentence of an answer must trace back to retrieved text from the corpus, and the answer must name its source — book · category.
  • One question, several bodies of knowledge. A single question can touch tafseer, hadith and fiqh at once. Those are different literatures with different conventions; one generic retriever flattens them.
  • Nothing leaves the machine. No hosted API. The whole stack — LLM, embeddings, reranker, vector store — runs on one box with a single consumer GPU.
Design constraint Retrieval quality is not something you can assume. If the chunks handed to an agent are thin, the agent will still write something confident. So the pipeline had to be able to notice that its evidence is weak, try again, and — if it still cannot do better — say so instead of hiding it.

That last point is what the rest of this page is really about: a per-category judge loop that sits between retrieval and generation, and a low_conf flag that survives all the way into the final answer.

01 · Architecture

One graph, six lanes, one answer

The whole thing is a LangGraph state graph. A question enters at a gate, fans out into six independent category lanes that run concurrently, and converges on a synthesizer. Every node is either an LLM call against the local endpoint or a retrieval step.

The six stages

1 · Gate node 1 LLM call

A single call does two jobs at once: decide whether the question is an Islamic question at all, and decompose it into distinct information needs. It returns structured JSON. If the question is out of scope, the graph jumps straight to the final-answer node with a polite decline — no retrieval, no agents, no GPU time spent.

2 · LLM router Structured output

Given the decomposed question, the router selects which of the six categories are actually relevant, and reformulates a sub-query per category in Urdu — the language the corpus and the users share.

3 · Parallel retrieval

One asyncio.gather over the active categories. Each lane runs its own vector search, reranks the candidates down to top-K anchors, then expands ±W neighbouring chunks around every anchor.

4 · Per-category judge loop Max 3

Each lane has its own LLM judge asking one question: are these chunks sufficient? If not, a rewriter expands the sub-query, the lane re-retrieves, merges and dedups, and the judge looks again — at most three times.

5 · Category agents

A LangGraph fan-out into six specialized agents. Each receives only its own chunks plus the low_conf flag its judge produced, and answers within its own literature.

6 · Synthesizer Short-term memory

Merges the category answers into one reply, hedges anything a judge marked low-confidence, keeps a sliding window of the last five turns for follow-ups, and attaches the citations.

Why a lane per category instead of one big retriever Tafseer, hadith, fiqh, adab, the letters of the imams and tareekh are different literatures. Separating them at the vector-store level means the router can switch a whole body of knowledge off for a question that does not need it — and the judge for each lane only has to reason about one kind of evidence at a time.
02 · Gate & Router

One call that decides, and one that dispatches

The cheapest way to protect a RAG system is to not run it. The gate node is a single LLM call placed before anything expensive, and it does double duty — scope check and query decomposition — because both need the same reading of the question.

The gate node

It emits structured JSON: an in-scope boolean, a short reason, and a list of sub-queries. If the question is not an Islamic question, the graph routes directly to the final-answer node with a polite refusal, and the six lanes never start. If it is — and especially if it is a compound question — the sub-query list is what the router works from.

Decline is a first-class branch, not an exception The refusal goes through the same final-answer node as a real answer. One exit means one place to format, log and return a response, and no path where the graph can hang half-finished.
nodes/gate.py
# ── Gate node: ONE call that classifies AND decomposes ───────────────
from typing import List
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class GateDecision(BaseModel):
    is_islamic: bool = Field(
        description='True only if the question concerns Islamic knowledge'
    )
    reason: str = Field(description='One short line, for the trace log')
    is_complex: bool = Field(description='True if it holds several needs')
    sub_queries: List[str] = Field(
        default_factory=list,
        description='Urdu sub-queries, one per distinct information need'
    )

# Everything points at the local vLLM endpoint, not a hosted API
local_llm = ChatOpenAI(
    model='Islamic-rag-model',
    base_url='http://localhost:8000/v1',
    api_key='EMPTY',
    temperature=0.0,
)
gate_llm = local_llm.with_structured_output(GateDecision)


async def gate_node(state: GraphState) -> dict:
    '''Relevance check + decomposition. Costs exactly one LLM call.'''
    decision = await gate_llm.ainvoke(
        GATE_PROMPT.format(
            question=state['question'],
            history=state['history'][-5:],     # sliding window
        )
    )

    if not decision.is_islamic:
        # Short-circuit: straight to the single exit node.
        return {
            'declined': True,
            'route': 'final_answer',
            'final_answer': POLITE_REFUSAL,
            'citations': [],
        }

    return {
        'declined': False,
        'route': 'router',
        'sub_queries': decision.sub_queries or [state['question']],
        'gate_reason': decision.reason,
    }

The router

The router is the second structured-output call. It maps the decomposed question onto the six categories, returning only those that are actually worth searching, and it writes each sub-query in Urdu — matching the language of both the users and the corpus, so the embedding model is comparing like with like rather than translating across a language boundary mid-pipeline.

  • Fewer lanes, faster answer — a purely historical question does not need to wake the fiqh lane
  • Better sub-queries — a hadith lane gets a sub-query phrased the way hadith literature is indexed, not the user's original sentence
  • Deterministic fan-out — the set of active categories is a typed list, so the graph builds the same node set every time
nodes/router.py
# ── Router: which categories, and what to ask each of them ───────────
from typing import Dict, List, Literal

CATEGORIES = [
    'tafseer', 'hadith', 'fiqh', 'etiquette', 'imam_letters', 'tareekh'
]
Category = Literal[
    'tafseer', 'hadith', 'fiqh', 'etiquette', 'imam_letters', 'tareekh'
]

class RoutePlan(BaseModel):
    active: List[Category] = Field(
        description='Only the categories that can genuinely contribute'
    )
    urdu_sub_queries: Dict[str, str] = Field(
        description='category -> reformulated sub-query, written in Urdu'
    )

router_llm = local_llm.with_structured_output(RoutePlan)


async def router_node(state: GraphState) -> dict:
    plan = await router_llm.ainvoke(
        ROUTER_PROMPT.format(
            question=state['question'],
            sub_queries=state['sub_queries'],
            categories=CATEGORIES,
        )
    )
    active = [c for c in plan.active if c in CATEGORIES] or CATEGORIES
    return {
        'active_categories': active,
        'sub_queries_by_cat': {
            c: plan.urdu_sub_queries.get(c, state['question'])
            for c in active
        },
    }
03 · Retrieval

Embeddings, metadata separation and neighbour expansion

Retrieval is where a grounded system is won or lost. Three choices carry most of the weight here: a multilingual embedding model, a vector store that knows which book every chunk came from, and an expansion step that refuses to hand an agent half a passage.

bge-M3 for the embeddings

BAAI/bge-M3 embeds both the corpus chunks and the Urdu sub-queries. It is multilingual and handles long inputs, which matters for a corpus that is not in English and for chunks that carry a fair amount of context. A reranker then re-scores the vector-search candidates against the sub-query — a cross-encoder look at query and chunk together, rather than the bi-encoder approximation the vector search gives you. The top-K survivors become the lane's anchors.

Qdrant, separated by metadata

Every chunk lands in Qdrant with a payload recording its book, its category and its position in that book. That payload is what makes the six lanes possible: retrieval is a filtered search, so the fiqh lane physically cannot return a chunk from a tareekh book, and the router can switch categories off without touching the index.

Neighbour expansion ±W

Chunking always cuts somewhere. If an anchor happens to be the second half of an argument, an agent reading it alone will answer from a fragment. So after reranking, each anchor is expanded: the chunks immediately before and after it in the same book are pulled in, giving a contiguous window of 2W + 1 chunks around every anchor. The book and chunk index in the payload are what make that lookup cheap.

Six lanes, one gather

The lanes have no reason to wait for each other, so the whole fan-out is a single asyncio.gather. Six vector searches, six rerank passes and six expansions overlap; the batching settings on the vLLM side (later on this page) are what let the LLM steps do the same.

retrieval.py
# ── Filtered retrieval → rerank → neighbour expansion, per category ──
import asyncio
from qdrant_client.models import Filter, FieldCondition, MatchValue

COLLECTION = 'islamic_corpus'
TOP_N   = 60      # candidates handed to the reranker
TOP_K   = 8       # anchors kept after reranking
WINDOW  = 2       # neighbouring chunks pulled either side of an anchor


async def search_category(category: str, sub_query: str) -> list:
    '''Vector search restricted to one category by payload filter.'''
    vector = await embedder.aembed_query(sub_query)          # bge-M3
    return await qdrant.asearch(
        collection_name=COLLECTION,
        query_vector=vector,
        query_filter=Filter(must=[
            FieldCondition(key='category',
                           match=MatchValue(value=category))
        ]),
        limit=TOP_N,
        with_payload=True,
    )


async def expand_neighbours(anchors: list, window: int = WINDOW) -> list:
    '''Pull chunk_id +/- window from the SAME book, then order and dedup.'''
    wanted = set()
    for a in anchors:
        book, idx = a.payload['book'], a.payload['chunk_id']
        for offset in range(-window, window + 1):
            wanted.add((book, idx + offset))

    neighbours = await qdrant.aretrieve_by_keys(COLLECTION, wanted)
    merged = dedup_by_key(anchors + neighbours)
    return sorted(merged, key=lambda c: (c['book'], c['chunk_id']))


async def retrieve_lane(category: str, sub_query: str) -> list:
    hits    = await search_category(category, sub_query)
    anchors = await reranker.arerank(sub_query, hits, top_k=TOP_K)
    return await expand_neighbours(anchors)


# ── The fan-out: every active category at the same time ──────────────
async def parallel_retrieval(state: GraphState) -> dict:
    active = state['active_categories']
    lanes  = [
        retrieve_lane(c, state['sub_queries_by_cat'][c]) for c in active
    ]
    results = await asyncio.gather(*lanes)
    return {'chunks_by_cat': dict(zip(active, results))}
Evaluated, not assumed The retrieval side is measured with a RAG evaluation pass over a held-out set of questions — checking whether the chunks a lane returns actually contain the answer, and whether the answer written from them stays inside those chunks. That is what the tuning of top-N, top-K and the expansion window was driven by, rather than intuition.
04 · The Judge Loop

Letting a lane admit its evidence is thin

This is the part of the system I find most interesting. Between retrieval and generation, every category lane runs its own LLM judge whose only job is to answer one question: can this question be answered from these chunks? If the answer is no, the lane does not shrug and generate anyway — it tries again.

The loop, step by step

  • Judge. An LLM call sees the sub-query and the accumulated chunks, and returns a sufficiency verdict plus a short note on what is missing.
  • Sufficient → the chunks go straight to that category's agent with low_conf = False.
  • Not sufficient, attempts remaining → a query rewriter expands or rephrases the sub-query using the judge's note about what was missing, the lane re-retrieves with the new phrasing, reranks the new candidates, then merges and dedups them into everything gathered so far — and the judge looks at the enlarged pool.
  • Still not sufficient at attempt 3 → the lane gives up trying and passes the pool on anyway, with low_conf = True.
Why the pool accumulates instead of being replaced Each retry merges into what the lane already has rather than starting over. A rewritten query often surfaces a different part of the same discussion, so the useful chunks from attempt 1 are still useful at attempt 3 — and dedup on (book, chunk_id) keeps the pool from doubling up on the neighbours it already pulled.

The retry logic

Each lane's loop is a plain async function, so all six loops are themselves gathered — a lane that passes on its first judge call is not held up by a lane on its third rewrite.

nodes/judge.py
# ── Per-category judge loop: retry, accumulate, then admit defeat ────
MAX_RETRIES = 3

class Verdict(BaseModel):
    sufficient: bool = Field(
        description='True if these chunks can answer the sub-query'
    )
    missing: str = Field(
        default='', description='What is absent, used by the rewriter'
    )

class Rewrite(BaseModel):
    sub_query: str = Field(description='Broader Urdu sub-query to retry')

judge_llm    = local_llm.with_structured_output(Verdict)
rewriter_llm = local_llm.with_structured_output(Rewrite)


async def judge_loop(category: str, sub_query: str, chunks: list) -> dict:
    '''Runs for ONE category. Returns chunks plus a confidence flag.'''
    pool    = chunks
    current = sub_query

    for attempt in range(1, MAX_RETRIES + 1):
        verdict = await judge_llm.ainvoke(
            JUDGE_PROMPT.format(
                category=category, sub_query=current, chunks=pool
            )
        )

        if verdict.sufficient:
            return {'category': category, 'chunks': pool,
                    'low_conf': False, 'attempts': attempt}

        if attempt == MAX_RETRIES:
            break                      # out of retries, fall through

        # Rewrite using WHAT THE JUDGE SAID WAS MISSING, then re-retrieve
        rewrite = await rewriter_llm.ainvoke(
            REWRITE_PROMPT.format(
                sub_query=current, missing=verdict.missing
            )
        )
        current = rewrite.sub_query
        fresh   = await retrieve_lane(category, current)
        pool    = dedup_by_key(pool + fresh)        # merge, never replace

    # Three failed verdicts: hand it over, but say so honestly.
    return {'category': category, 'chunks': pool,
            'low_conf': True, 'attempts': MAX_RETRIES}


# ── All six judge loops run concurrently, same as retrieval ──────────
async def judge_all(state: GraphState) -> dict:
    loops = [
        judge_loop(c, state['sub_queries_by_cat'][c],
                   state['chunks_by_cat'][c])
        for c in state['active_categories']
    ]
    graded = await asyncio.gather(*loops)
    return {'graded_by_cat': {g['category']: g for g in graded}}
The flag is the point low_conf is not a log line. It travels with the chunks into the category agent, and then into the synthesizer, where it changes how that category's contribution is worded in the final answer. A weakly-evidenced category gets hedged rather than quietly presented with the same confidence as a well-evidenced one.
05 · Agents & Synthesis

Six answers, one reply, and memory that knows its place

Once a lane's judge has ruled, LangGraph fans out into the category agents. Each agent is a small specialist: its own prompt, its own conventions, and a context window containing only its own chunks plus the low_conf flag. A hadith agent is not asked to reason about jurisprudence, and a fiqh agent never sees tareekh chunks it might drift into.

tafseer_agent

Answers from commentary literature, staying with the exegesis the retrieved passages actually give.

hadith_agent

Works from narration collections, reporting what the retrieved text states rather than generalising.

fiqh_agent

Handles questions of practice, keeping to the rulings present in its own chunks.

etiquette_agent

Covers adab and conduct material from the books assigned to that category.

imam_letters_agent

Draws on the letters and writings grouped under that category in the corpus.

tareekh_agent

Historical material — events, sequence and context as the retrieved sources record them.

Short-term memory: a sliding window of five turns

The synthesizer keeps the last five turns of the conversation, and nothing more. That is enough for the thing conversational memory is actually needed for — resolving "what about the second one?" or "and in that same chapter?" — without letting an ever-growing transcript compete with the retrieved chunks for the model's attention, or eat into a 12k context window that the evidence needs.

Crucially, memory resolves the question, never the answer. A follow-up is rewritten into a standalone question using the window, and then goes through the same gate, router, retrieval and judging as any other question. The books remain the only source of substance.

How a low-confidence category reaches the reader

The synthesizer receives one answer per active category, each tagged with its flag. Well-evidenced categories are merged normally. A category whose judge never reached sufficiency is hedged — presented as what the retrieved material suggests rather than as a settled statement — and its citations still name the book and category so a reader can go and check. Then the answer and the user's turn append to the window.

Wiring it up

All of it is one LangGraph StateGraph. The gate's conditional edge is the only branch; everything after the router is a fan-out and a fan-in.

graph.py
# ── The LangGraph state machine ──────────────────────────────────────
from langgraph.graph import StateGraph, START, END

WINDOW_TURNS = 5          # short-term memory: last 5 turns only


async def category_agents(state: GraphState) -> dict:
    '''Fan-out: each agent sees ONLY its own chunks and its own flag.'''
    graded = state['graded_by_cat']
    runs = [
        AGENTS[cat].ainvoke({
            'sub_query': state['sub_queries_by_cat'][cat],
            'chunks':    g['chunks'],
            'low_conf':  g['low_conf'],
        })
        for cat, g in graded.items()
    ]
    answers = await asyncio.gather(*runs)
    return {'answers_by_cat': dict(zip(graded.keys(), answers))}


async def synthesizer(state: GraphState) -> dict:
    '''Merge, hedge anything low_conf, cite, and roll the window.'''
    if state['declined']:                  # the gate's short-circuit
        return {'final_answer': state['final_answer'], 'citations': []}

    parts = [
        {'category': cat,
         'answer':   a['text'],
         'hedge':    state['graded_by_cat'][cat]['low_conf'],
         'sources':  a['sources']}          # book + category per chunk
        for cat, a in state['answers_by_cat'].items()
    ]
    final = await local_llm.ainvoke(
        SYNTH_PROMPT.format(
            question=state['question'],
            history=state['history'][-WINDOW_TURNS:],
            parts=parts,
        )
    )
    history = (state['history'] + [(state['question'], final.content)])
    return {
        'final_answer': final.content,
        'citations': collect_citations(parts),
        'history': history[-WINDOW_TURNS:],     # slide the window
    }


graph = StateGraph(GraphState)
graph.add_node('gate', gate_node)
graph.add_node('router', router_node)
graph.add_node('retrieve', parallel_retrieval)
graph.add_node('judge', judge_all)
graph.add_node('agents', category_agents)
graph.add_node('final_answer', synthesizer)

graph.add_edge(START, 'gate')
graph.add_conditional_edges(
    'gate',
    lambda s: s['route'],                 # 'router' or 'final_answer'
    {'router': 'router', 'final_answer': 'final_answer'},
)
graph.add_edge('router', 'retrieve')
graph.add_edge('retrieve', 'judge')
graph.add_edge('judge', 'agents')
graph.add_edge('agents', 'final_answer')
graph.add_edge('final_answer', END)

app = graph.compile()
06 · Serving

A 14B model, six concurrent agents, one RTX 3090 Ti

Every LLM call in this system — the gate, the router, six judges, the rewriters, six agents and the synthesizer — hits the same local endpoint. There is no hosted API anywhere in the pipeline, which means the serving configuration is not an afterthought: it is the thing that decides whether the architecture is even runnable.

Qwen3-14B-AWQ is served with vLLM in a container, exposing an OpenAI-compatible endpoint that LangChain talks to unchanged. A 14B model in fp16 would not fit on a 24 GB card alongside a KV cache large enough for six concurrent requests, so the configuration trades precision for room in the places where precision costs least.

The deployment command

serve.sh
docker run --gpus all \
  --ipc=host \
  --restart unless-stopped \
  -p 8000:8000 \
  -v /mnt/f/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen3-14B-AWQ \
  --quantization awq_marlin \
  --kv-cache-dtype fp8 \
  --max-model-len 12000 \
  --gpu-memory-utilization 0.93 \
  --enable-prefix-caching \
  --max-num-seqs 16 \
  --max-num-batched-tokens 65536 \
  --served-model-name Islamic-rag-model

What each flag is buying

WeightsAWQ 4-bit
--quantization awq_marlin — the model is an AWQ 4-bit checkpoint, so the weights occupy roughly a quarter of what fp16 would need. That is what makes a 14B model fit on a 24 GB card with room left over. awq_marlin selects the Marlin kernels for AWQ, which are considerably faster than the reference AWQ path on Ampere-class hardware.
KV cachefp8
--kv-cache-dtype fp8 — the attention cache is stored at 8-bit instead of 16-bit. The cache, not the weights, is what grows with context length and concurrency, so halving its footprint is what lets six long-context requests coexist.
Context12k tokens
--max-model-len 12000 — sized for the real payload: a system prompt, a handful of conversation turns and an expanded chunk window. Capping it deliberately keeps the per-sequence cache budget predictable instead of letting one request starve the others.
VRAM93%
--gpu-memory-utilization 0.93 — vLLM pre-allocates this fraction of the card for weights plus KV cache. Pushing it to 0.93 hands almost the whole GPU to the server; the remaining headroom covers the display and other processes on the box.
Prefix cachereuse
--enable-prefix-caching — the six category agents and the six judges share long, identical instruction prefixes. With prefix caching, that shared prefix is prefilled once and reused, instead of being recomputed on every one of the dozen-plus calls a single question triggers.
Batchingthroughput
--max-num-seqs 16 and --max-num-batched-tokens 65536 — the scheduler keeps up to 16 sequences in flight and can pack 65,536 tokens into a batched step. That is what turns six parallel category calls from six sequential generations into one continuous batch.
Cache mountpersistence
-v /mnt/f/huggingface:/root/.cache/huggingface — model weights live on the host, so recreating the container does not re-download tens of gigabytes.
Lifecyclealways-on
--restart unless-stopped keeps the endpoint up across reboots and crashes; --ipc=host gives the container the shared memory that the worker processes need; -p 8000:8000 is the OpenAI-compatible port LangChain points at.
The trade being made 4-bit weights and an 8-bit KV cache are lossy. The reason it is an acceptable trade here is that the model is not being asked to recall facts from its parameters — it is being asked to read retrieved passages and write from them. Grounding does the work that precision would otherwise have to.
07 · Outcomes

What the architecture buys

Answers you can check

Every answer names the book and the category it came from, and the metadata separation in Qdrant is what makes that citation trustworthy rather than decorative.

Honest about weak evidence

The judge loop gives a lane three chances to find better material, and a way to say it did not. Low-confidence categories reach the reader hedged, not disguised.

Specialists, not one generalist

Six agents with six prompts and six filtered corpora keep each literature's conventions intact, and keep one category's material from leaking into another's answer.

Entirely self-hosted

Model, embeddings, reranker and vector store all run on one machine with one consumer GPU. No per-token cost, no data leaving the box, no dependency on an external provider.

What I would revisit next

  • A hybrid retrieval pass — sparse lexical matching alongside the dense vectors — for questions that hinge on a specific term the embedding smooths over
  • Adaptive W: expanding further around an anchor when the judge's complaint is specifically about truncated context, rather than using a fixed window everywhere
  • Persisting the graph state to a checkpointer so conversations survive a restart, instead of holding the window in process memory
  • Turning the RAG evaluation pass into a scheduled run, so a change to chunking, prompts or the reranker is caught by a regression rather than by a user
