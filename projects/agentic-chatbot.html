The Problem

A website visitor has a question. Sales needs a lead.

A corporate website answers the same questions all day: what do you build, what does it cost, which industries have you worked in, can I talk to someone. Those conversations are valuable — but only if they end in a qualified lead that reaches the sales team with its full context.

The goal was a chatbot that behaves like an informed team member rather than an FAQ widget: it understands follow-up questions, routes each query to the right body of knowledge, refuses to answer things outside its remit, and turns genuine interest into a CRM record that sales can act on — with the entire conversation attached.

Design constraint Everything had to be debuggable. An agent that occasionally gives a wrong answer with no way to find out why is not something you can put in front of customers.
01 · Architecture

Choosing the agentic pattern: why ReAct

Several agentic patterns were on the table. For a customer-facing bot that has to answer diverse questions, collect leads, route to the right information and survive mid-conversation changes of direction, I chose ReAct (Reasoning + Acting).

What ReAct actually does

ReAct interleaves reasoning with action in a loop. Instead of running a fixed pipeline, the model reasons about what to do next, calls a tool, observes the result, and reasons again until it can answer:

Thought → Act → Observe → Thought → Act → Observe → … → Final Answer The agent decides which tools to invoke from user intent, conversation history and previous tool output — not from a hardcoded route.

What I ruled out, and why

Single-prompt chaining Rejected

One LLM call carrying every service description, price and portfolio link. Context bloat, high token cost per turn, and no structured way to take an action.

Plan-and-execute Rejected

Plans all steps upfront, then executes. Brittle in conversation, where the visitor changes direction halfway through.

Static tool routing Rejected

Hardcoded rules mapping queries to handlers. Fails on ambiguous phrasing and cannot follow up naturally.

Multi-agent coordination Rejected

Several specialized agents negotiating with each other. Genuine overkill for a single-domain bot, and much harder to debug and maintain.

ReAct single agent Chosen

One coherent reasoning loop with full agency over a toolbox. Handles ambiguity and follow-ups, keeps each tool small and testable, and produces a readable trace of every decision.

The LLM as a query router

The model sits at the centre as an orchestrator. Every message arrives with the conversation history and the full tool list, and the model reads intent, picks the domain expert that can answer, calls it with parameters, observes the output and composes the reply. It is not just generating text — it is dispatching to specialized handlers, which is what keeps hallucination down and business logic testable.

Agent initialization

LangGraph's prebuilt ReAct constructor wraps the model with all registered tools and a checkpointer that persists conversation state per session thread. Temperature is pinned to zero — routing decisions should be deterministic, not creative.

agent.py
# ── ReAct agent initialization ───────────────────────────────────────
from langchain_openai import ChatOpenAI
from langgraph.prebuilt import create_react_agent
from langgraph.checkpoint.memory import MemorySaver

# Short-term memory: conversation state, keyed per session thread
checkpointer = MemorySaver()

llm = ChatOpenAI(
    model='gpt-4o',
    temperature=0.0,      # deterministic routing, no invented detail
    max_tokens=500
)

# Every tool is a focused domain expert with its own knowledge
tools = [
    handle_greeting,              # small talk
    services_info,                # knowledge: service catalogue
    company_portfolio,            # knowledge: work by domain
    industries_served,            # knowledge: verticals
    pricing_info,                 # knowledge: engagement models
    contact_info,                 # knowledge: how to reach us
    awards, about_company,        # knowledge: company background
    founders_and_teams,           # knowledge: who you'd work with
    client_reviews,               # knowledge: ratings and reviews
    podcasts_and_blogs,           # knowledge: published content
    job_opportunities,            # knowledge: careers enquiries
    business_recommendations,     # maps an industry to services
    show_lead_form,               # action: capture a project lead
    show_consultation_form,       # action: book a consultation
    show_sales_form,              # action: connect to sales
    show_issue_form,              # action: report a site issue
    handle_irrelevant_queries,    # guardrail: out-of-scope filter
]

agent_executor = create_react_agent(
    model=llm,
    tools=tools,
    checkpointer=checkpointer,    # enables memory across turns
    state_modifier=system_prompt  # business context + routing rules
)

# One isolated thread per visitor session
config = {'configurable': {'thread_id': thread_id}}
response = agent_executor.invoke(
    {'messages': [HumanMessage(content=user_input)]},
    config=config
)
02 · Tools

18 small experts instead of one enormous prompt

The most common mistake in LLM chatbots is loading everything into a single system prompt — every service description, price table, portfolio link and form rule in one context window. That fails in two ways at once:

Context rot & context bloat As context grows, attention degrades on its earlier parts and instructions get quietly "forgotten" in long conversations. Meanwhile every single turn pays for tokens it does not need.

The fix is specialization. Each tool is a compact domain expert with its own prompt template and curated knowledge, and the agent loads only what the current question needs. That buys five things:

  • Lower token cost — only the relevant tool's knowledge is processed per query
  • Higher accuracy — each tool is tuned for one domain, with no dilution
  • Easier maintenance — update one tool's knowledge without touching the agent
  • Real testability — each tool can be unit-tested in isolation
  • Cleaner guardrails — out-of-scope queries get their own dedicated handler

A · Knowledge tools

These combine curated company data with generation, so answers stay grounded but still read conversationally.

services_info

The full service catalogue — web, mobile, AI, DevOps, cybersecurity, QA — answered against a curated data string.

company_portfolio

Validates that a service or industry is actually offered, then returns the matching portfolio link.

industries_served

Deep dives per vertical — healthcare, fintech, logistics, education, hospitality — plus links for the rest.

pricing_info

Engagement models and estimates, including objection handling for price-sensitive visitors.

contact_info

Office and contact details, with a strict policy on what may and may not be shared.

business_recommendations

Maps a visitor's stated industry to the most relevant services: "I'm in healthcare — how can you help?"

B · Action tools — where conversation becomes pipeline

Action tools return a signal string rather than prose. The backend intercepts that signal and renders an interactive form; the submission is written straight into the CRM tables.

show_lead_form

Visitor wants to start a project. Validates that the request is software-related, then opens lead capture → leads.

show_consultation_form

Books a consultation with session id, name, email and type → consultations.

show_sales_form

Connects the visitor to sales with their reason for getting in touch → sales.

show_issue_form

Captures website problems with a description → issues.

Conversation-to-lead tracing Every submission carries the visitor's session id, and a conversation tracker writes each message, response, button click and form submit to the history table. Sales doesn't just get an email address — they get the entire conversation that led to it.
tools.py
# ── Knowledge tool: curated data + generation ────────────────────────
@tool
def services_info(user_message: str = '') -> str:
    '''Service enquiries: web, mobile, AI, DevOps, cybersecurity.'''
    services_data = '''
    1. Web Development   — custom websites and web apps
    2. Mobile            — iOS, Android, cross-platform
    3. AI Integration    — ML, chatbots, NLP, computer vision
    4. Cybersecurity     — audits, penetration testing, compliance
    5. DevOps            — CI/CD, containers, infrastructure
    ... (full catalogue with descriptions)
    '''
    prompt = PromptTemplate(
        template='You are the website assistant... {services_data} ... {user_message}',
        input_variables=['user_message', 'services_data']
    )
    return (prompt | llm).invoke({
        'user_message': user_message,
        'services_data': services_data
    }).content


# ── Action tool: returns a signal, not prose ─────────────────────────
@tool
def show_lead_form() -> str:
    '''Visitor wants to start a software project. Validates the request
    is tech-related, then asks the frontend to render the lead form.'''
    return 'SHOW_LEAD_FORM'


# ── Backend intercepts the signal and routes to a form ───────────────
def process_user_message(user_input, session_id, thread_id):
    response = agent_executor.invoke(
        {'messages': [HumanMessage(content=user_input)]},
        config={'configurable': {'thread_id': thread_id}}
    )
    for msg in reversed(response['messages'][-3:]):
        if type(msg).__name__ == 'ToolMessage':

                return {'show_form': 'lead', 'response': ''}
            if 'SHOW_CONSULTATION_FORM' in msg.content:
                return {'show_form': 'consultation', 'response': ''}
    return {'show_form': None, 'response': agent_response}

03 · Memory

What separates an agent from a chatbot

Without memory, every message is an isolated event. Ask about web development, then follow up with "what's the pricing for that?" — and "that" means nothing. The conversation breaks exactly where it was getting interesting.

The bot runs two complementary tiers, because they solve different problems:

Short-term memory — the conversation

Active history within one session, so the agent resolves follow-ups, pronouns and context switches. In LangGraph this is a checkpointer keyed by a unique thread_id per visitor. Invoke with the same thread id and the full history comes back automatically.

Long-term memory — the business record

Structured data that outlives the session: leads, consultations, sales contacts, issues and complete conversation histories, all in PostgreSQL, joined by session id.

The combination is the point Short-term memory means the bot remembers you inside this conversation. Long-term memory means the sales team can read that whole conversation next week. Together they turn a chatbot into a lead generation engine.

class ConversationTracker:
    @staticmethod
    def track_user_message(session_id, user_message):
        cursor.execute('''
            INSERT INTO conversation_history
                (session_id, timestamp, message_type, user_message)
            VALUES (%s, %s, %s, %s)
        ''', (session_id, datetime.now(), 'user_message', user_message))
04 · Guardrails

Defining what the bot should not answer

Once the toolbox covers every business domain, a different problem appears: visitors ask about the weather, how to fix their phone, crypto prices, or how machine learning works. None of that belongs to a company website assistant — and left unguarded, the model will happily answer, off-brand and sometimes wrong.

A guardrail is a boundary, not a filter It defines what the assistant can do versus what it should not do, and makes sure both cases are handled gracefully.

Implemented as a tool, not a wrapper

The guardrail is a tool — handle_irrelevant_queries — so it lives inside the same ReAct loop as everything else. The model classifies each query and routes out-of-scope ones to it. The system prompt makes that mandatory for general knowledge, unrelated tutorials, hardware problems, non-software services and personal advice.

The tool then produces a short, polite redirect that acknowledges the question, states the assistant's scope and offers a relevant next step — rather than a blunt refusal.

guardrails.py
# ── Guardrail tool ───────────────────────────────────────────────────
@tool
def handle_irrelevant_queries(user_message: str = '') -> str:
    '''Handles ANY query outside the company's business scope.
    Triggered by the model when it judges a question out of scope.

    Examples:
      - General knowledge: 'What is the capital of France?'
      - Hardware:          'How do I fix my phone?'
      - Non-software:      'Can you build me a smart watch?'
      - Personal advice:   'Good meditation techniques?'
    '''
    irrelevant_prompt = PromptTemplate(
        template='''You are the website assistant.
        USER MESSAGE: {user_message}
        RESPONSE PATTERNS:
          1. Hardware issue  -> apologise, point to the manufacturer.
          2. Non-software    -> we build software and AI; offer that instead.
          3. General query   -> acknowledge, redirect to our services.
        Keep it to 1-2 sentences. End with an invitation.''',
        input_variables=['user_message']
    )
    return (irrelevant_prompt | llm).invoke(
        {'user_message': user_message}
    ).content


# ── Enforced from the system prompt ──────────────────────────────────
system_prompt = '''
CRITICAL QUERY VALIDATION — APPLY BEFORE EVERY RESPONSE:

RELEVANT (use the appropriate tool):
  - services, portfolio, pricing, team, awards, contact
  - hiring us, consultations, sales, issue reports
  - software / web / mobile / AI / cloud enquiries

IRRELEVANT (MUST call handle_irrelevant_queries):
  - general knowledge, tutorials, personal advice
  - hardware, physical construction, non-tech services
  - ANY topic outside the company's business

RULE: if the query is about anything else, call the
guardrail tool IMMEDIATELY.
'''

LangGraph also offers interrupt-based human-in-the-loop guardrails for flagging sensitive queries to a person. For this bot I chose the tool-based route, because it keeps the experience fully automated and instant.

05 · Testing & Observability

Making a probabilistic system debuggable

You cannot unit-test an agent with exact expected strings — responses are probabilistic and context-dependent. What you can do is benchmark behaviour against a custom evaluation dataset, and trace every run in production.

The evaluation dataset

Representative question-and-expectation pairs across every tool domain:

  • Knowledge: "What services do you offer?" → mentions web, mobile, AI, DevOps, security
  • Action trigger: "I want to build a website" → emits the lead-form signal
  • Guardrail: "What is the capital of France?" → polite redirect, no invented answer
  • Follow-up context: "Tell me about web services" → "What's the pricing?" → web-specific pricing
  • Industry routing: "I'm in healthcare, how can you help?" → healthcare-relevant recommendations

Runs are scored on tool-selection accuracy, response relevance, hallucination rate and form-trigger accuracy.

Release bar Above 90% correct tool routing on the evaluation set before going live, and re-evaluation after every new tool or prompt change, so regressions surface before customers meet them.

Tracing: the black box, opened

When someone reports a wrong answer, guessing is not a debugging strategy. Tracing captures a complete execution record per invocation — the input, the reasoning at each step, every tool call and its output, the final response, plus token usage, latency and cost. Enabling it takes three environment variables, and instrumentation is automatic from there.

Step 1Reason
Input: system prompt + message + history → "asks about AI services → call services_info"
Step 2Act
Tool: services_info(user_message='What are your AI services?') · latency 1.2s
Step 3Observe
Returns the curated AI capability list — ML, chatbots, NLP, computer vision, generative AI
Step 4Respond
Final reply composed · total 2.1s · 847 tokens · $0.004

# ── Tracing: three variables, zero code changes ──────────────────────
import os
from dotenv import load_dotenv

load_dotenv()
os.environ['LANGCHAIN_API_KEY']   = os.getenv('LANGCHAIN_API_KEY')
os.environ['LANGCHAIN_PROJECT']   = os.getenv('LANGCHAIN_PROJECT')
os.environ['LANGCHAIN_TRACING_V2'] = 'true'

# Every agent.invoke() is now traced automatically.


# ── Benchmarking against the evaluation dataset ──────────────────────
from langsmith import Client
from langsmith.evaluation import evaluate

client  = Client()
dataset = client.create_dataset('website-chatbot-evals')

client.create_examples(
    inputs=[
        {'message': 'What web development services do you offer?'},
        {'message': 'I want to build a mobile app'},
        {'message': 'What is the capital of France?'},   # guardrail test
    ],
    outputs=[
        {'expected_tool':   'services_info'},
        {'expected_signal': 'SHOW_LEAD_FORM'},
        {'expected_tool':   'handle_irrelevant_queries'},
    ],
    dataset_id=dataset.id
)

results = evaluate(
    lambda inputs: agent_executor.invoke(
        {'messages': [HumanMessage(content=inputs['message'])]}
    ),
    data=dataset.name,
    evaluators=['tool_selection_accuracy', 'response_relevance'],
    experiment_prefix='chatbot-v1'
)
06 · Outcomes

What the architecture buys

Context-aware conversation

Short-term memory per session means follow-ups, pronouns and mid-conversation direction changes all resolve naturally.

Leads with their context attached

Form submissions land in the CRM alongside the full conversation, so sales opens a lead already knowing the story.

Deterministic debugging

Every answer has a trace: which tool ran, what it returned, what it cost. Wrong answers get diagnosed, not guessed at.

Cheap to extend

A new domain is a new tool with its own prompt and knowledge — no rewrite of the agent, no growing mega-prompt.

What I'd revisit next

  • Moving session state to a database-backed checkpointer, so conversations survive a restart rather than living in process memory
  • Retrieval over the knowledge tools as the catalogue grows, instead of curated strings per tool
  • Automatic nightly evaluation runs, so prompt or model drift is caught by CI rather than by a customer
