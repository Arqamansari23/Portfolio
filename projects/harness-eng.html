The Problem

Equity research is four jobs pretending to be one

Writing a research note on a listed company means reading hundreds of pages of filings, listening to three earnings calls, mapping a competitive set, and then building a model that ties all of it to a number. Each of those is a different reading mode, a different set of sources, and a different way to be wrong.

The obvious way to automate it is one agent with twenty tools. That agent drowns: a single 10-K dump fills its context window, the transcript analysis then competes with the filing text for attention, and by the time it reaches the valuation it has quietly forgotten the instructions it was given at the start.

So the design question is not "can an LLM read a 10-K" — it is how much of a multi-agent system do you actually have to write yourself? My answer here was: as close to none of it as possible.

Where this project actually stands — read this first This is a step-1 scaffold in active development, not a shipped product. The graph construction is verified: create_deep_agent() really does compile a LangGraph graph with the skills, memory and human-in-the-loop middleware attached. The MCP tools are still a placeholder, the sandbox backend is unset, and the approval gate is designed but not wired. Nothing below claims otherwise, and section 6 is a line-by-line status table.
01 · Design Principle

The interesting decision was what not to build

Every multi-agent project I have read starts by writing an orchestrator: a loop that picks a worker, a message bus between workers, a store for intermediate results, a retry policy, a way to persist state. That code is the fun part, and it is almost entirely a re-implementation of things deepagents and LangGraph already ship.

So the rule for this build was simple: if the framework has a parameter for it, I do not write code for it. Delegation, progressive-disclosure skills, long-term memory, persistence and human-in-the-loop are all arguments to a single constructor. What is left for me is the part that is actually specific to equity research — the roles, the prompts, the methodology files, and the judgement about where a human has to stay in the loop.

What I ruled out, and why

Hand-rolled orchestrator loop Rejected

A Python loop that classifies the request, calls worker functions and merges their output. Every failure mode — partial results, retries, resumption after a crash — becomes mine to solve, badly, a second time.

Raw LangGraph nodes and edges Rejected

Perfectly viable, and it is what sits underneath anyway. But hand-drawing the graph means hand-maintaining state schemas and interrupt plumbing for a topology that a higher-level API already expresses in a list.

One ReAct agent with twenty tools Rejected

Cheapest to start, worst to scale. Every source a tool returns lands in the same window, so filings, transcripts and peer data all compete for the same attention budget. This is the exact failure the project exists to avoid.

deepagents, configured not coded Chosen

Subagents, skills, memory, checkpointing and interrupts are constructor parameters. The architecture becomes reviewable in one screen of configuration, and the framework owns the hard parts — isolation, persistence and resumption.

What that buys on a resume, honestly Not "I built an agent framework." It is "I can tell which parts of an agent system are already solved, and I spent my effort on the parts that are not" — the role definitions, the methodology encoded as skills, and the decision about where the human signs off.
02 · Architecture

One lead analyst, four specialists, one constructor call

The main agent is the lead analyst. It never reads a filing itself. It plans with write_todos, delegates each unit of work to the subagent whose description best matches it, and synthesises the returned briefs into a draft note. Firm conventions arrive from AGENTS.md at startup; every step of the graph is written to a checkpointer as it completes.

The constructor is the architecture

There is no orchestration module in this repo, because there is nothing for it to do. Delegation, skill loading, memory injection, persistence and interrupts are all arguments here:

agent.py
# ── The entire harness is one constructor call ───────────────────────
import os
from deepagents import create_deep_agent
from langgraph.checkpoint.sqlite import SqliteSaver

from subagents import (
    SEC_FILINGS_ANALYST,
    COMPETITOR_RESEARCH_AGENT,
    EARNINGS_TRANSCRIPT_ANALYST,
    FINANCIAL_MODELING_AGENT,
)


def build_agent(checkpointer):
    return create_deep_agent(
        model=os.environ['ANTHROPIC_MODEL'],   # set in .env
        system_prompt=LEAD_ANALYST_PROMPT,     # lead analyst, not a doer
        tools=mcp_tools,                       # STUB: placeholder server

        # Delegation: four roles, each with its own context window
        subagents=[
            SEC_FILINGS_ANALYST,
            COMPETITOR_RESEARCH_AGENT,
            EARNINGS_TRANSCRIPT_ANALYST,
            FINANCIAL_MODELING_AGENT,
        ],

        # Progressive disclosure: SKILL.md files, loaded on demand
        skills=['./skills'],

        # Long-term memory: desk conventions injected at startup
        memory=['./AGENTS.md'],

        # Durability: every graph step committed as it completes
        checkpointer=checkpointer,

        # Human-in-the-loop. TODO: a publish_report tool set to True,
        # so the graph pauses before anything is finalised.
        interrupt_on={'task': False},

        # TODO: backend=... a sandbox so `execute` can run pandas.
        # Unset today, which means `execute` errors if it is called.
    )


# VERIFIED: with an InMemorySaver and no API key, this compiles a real
# LangGraph graph with the skills, memory and HITL middleware attached.
# NOT VERIFIED: an end-to-end run. That needs step 1 and 2 of the plan.

A subagent is a dict, not a class hierarchy

Each role is four fields. The description is load-bearing: it is what the lead agent reads when it decides where to route a task, so it is written as a routing contract rather than a summary. The prompt carries the working rules, and tools scopes what that role can touch — the modelling agent cannot browse, the research agent cannot execute code.

subagents.py
# ── Role definitions: config, not code ───────────────────────────────

SEC_FILINGS_ANALYST = {
    'name': 'sec-filings-analyst',
    # The description is the routing contract the lead agent reads.
    'description': (
        'Reads 10-K, 10-Q and 8-K filings for one ticker and reports '
        'material risks, segment performance and accounting red flags. '
        'Delegate here whenever an answer depends on primary filings.'
    ),
    'prompt': '''You are an SEC filings analyst.
    Work the red-flag-checklist skill before you conclude anything.
    Return at most 600 words: findings first, then the exact filing
    sections you relied on. Never speculate beyond the text. If a
    number is not in the filing, say so instead of estimating.''',
    'tools': ['edgar_search', 'read_file', 'write_file'],

03 · Context Isolation

Why four windows beat one big one

Subagents are not about parallelism here. They are about keeping a 214-page filing out of everyone else's head.

In a single-agent design, every artefact the agent touches stays in the transcript: the system prompt, the tool schemas, the full text of the 10-K, three transcripts, a dozen competitor pages. Attention degrades across a long context, and the instructions given at the top are the ones that fade first — right when the agent reaches the valuation and most needs its rules.

A subagent gets a fresh window and a scoped toolset. It reads whatever it has to read, and returns a short brief. The lead analyst accumulates four briefs, not four dumps.

  • Scoped tools — the modelling agent has no browser, the research agent has no code execution. Fewer tools per role means less routing ambiguity too.
  • Blast radius — a subagent that gets lost in a bad document burns its own window and returns a weak brief, rather than corrupting the whole run.
  • Routing by description — adding a fifth role is a dict, not a rewrite of the lead prompt.
What is not proven yet That the four descriptions route cleanly against real requests. Routing quality between subagents only shows up in an end-to-end run, and that needs real tools behind them — the first two roadmap items.
04 · Skills, Memory & the Gate

Methodology as files, approval as an interrupt

Domain methodology is the other thing that bloats a system prompt. DCF conventions, the red-flag checklist for a filing, how this desk treats terminal growth — all of it is important, and almost none of it is relevant on any given step.

Skills solve that with progressive disclosure. Each methodology lives in a SKILL.md file under ./skills. At startup only the name and one-line description enter the context; the body is pulled in by the subagent that actually needs it, into that agent's window.

Memory is two tiers. AGENTS.md is long-term: firm conventions that are true on every run, injected at startup. Thread-scoped state is short-term: the todos, the intermediate briefs and the message history for this one piece of research.

A skill is a file a human can review

That is the underrated part. Valuation conventions written into a prompt string are invisible to the analyst whose conventions they are. Written as a file, they can be read, argued with and version-controlled by someone who has never opened the agent code.

skills/dcf-methodology/SKILL.md
---
name: dcf-methodology
description: Build and sanity-check a DCF for a listed company. Use
  when asked for intrinsic value, a valuation range, or a WACC.
---

# DCF methodology

## When this desk uses a DCF
Only for companies with positive, forecastable operating cash flow.
For pre-profit names, use comparables and say so in the note.

## Required inputs
- 5 years of historical free cash flow, from the cash-flow statement
- Segment revenue split, from the most recent 10-K
- Net debt and diluted share count, as of the last reported quarter

## House conventions
- Risk-free rate: the current 10Y treasury, not a long-run average
- Terminal growth: capped at 2.5 percent. Anything higher needs a
  written justification printed in the output.
- Always produce a sensitivity grid: WACC plus or minus 1.0 point
  against terminal growth plus or minus 0.5 point.

## Output contract
Return the base case, the grid, and the three assumptions the
valuation is most sensitive to. Flag every figure you estimated
rather than sourced, and name the source for the ones you did.
Why the gate matters more than the model An agent that can research is useful. An agent that can research and publish is a liability. The planned publish_report interrupt is the difference: a tool that exists only to be intercepted, so the graph physically cannot finalise a note without a human decision. It is item 3 on the build plan, and it is the property that makes this project defensible rather than merely impressive.
05 · Durability

A long research run has to survive being interrupted

A multi-subagent run is a sequence of expensive steps. If the process dies at step four — a laptop sleeps, a rate limit hits, someone presses Ctrl-C — restarting from zero means re-reading the filing and re-paying for every token that already produced a good result.

LangGraph checkpointing removes that failure mode without any code of mine. Each completed step is committed to the checkpointer against a thread_id. Rerun with the same id and the graph reloads the last committed state and continues from there.

The context-manager detail SqliteSaver.from_conn_string() returns a context manager, not a saver. Building the agent outside the with block hands it a connection that is already closed — a quiet, confusing failure. The agent is therefore constructed inside the block, which also means the whole run lives inside it.
run.py
# ── Crash-resumable runs: the thread_id is the whole trick ───────────
import sys
from langgraph.checkpoint.sqlite import SqliteSaver
from agent import build_agent

THREAD_ID = 'tsla-research-01'

# from_conn_string returns a context manager. Build the agent INSIDE
# it, or the graph gets a connection that is already closed.
with SqliteSaver.from_conn_string('./checkpoints.sqlite') as checkpointer:

    agent  = build_agent(checkpointer)
    config = {'configurable': {'thread_id': THREAD_ID}}

    result = agent.invoke(
        {'messages': [{'role': 'user', 'content': sys.argv[1]}]},
        config=config,
    )

    print(result['messages'][-1].content)

# Kill the process at step 4, then run the exact same command again.
# LangGraph reloads the last committed checkpoint for THREAD_ID and
# continues from step 4 instead of re-running steps 1 to 3.
#
# Postgres is the same three lines:
#     from langgraph.checkpoint.postgres import PostgresSaver
#     with PostgresSaver.from_conn_string(DATABASE_URL) as checkpointer:
# Same API, different connection string.

07 · Roadmap

Five steps, in the order they unblock each other

The order is not arbitrary. Nothing can be evaluated end to end until the tools are real, so MCP comes first. The sandbox comes next because the modelling role is the only one that is hard-blocked without it. The approval gate comes before durability work, because it is the safety property — and durability of an unsafe system is not an improvement.

Step 1Real MCP servers
Replace the placeholder Brave Search server. The wrinkle: SEC EDGAR has no official MCP server, so this likely means wrapping EDGAR's REST and full-text-search API as a custom MCP server — or, as a faster first cut, a general web-search MCP server plus a plain LangChain tool for EDGAR. Until this lands, nothing can be evaluated end to end.
Step 2Sandbox backend
Set backend= to a sandbox (Daytona or Modal, per the deepagents sandboxes docs) so execute actually runs pandas and numpy. Test with a deliberately trivial DCF before letting the modelling agent near real figures — if a three-line discount calculation does not come back clean, nothing downstream is trustworthy.
Step 3Real HITL gate
Add a publish_report tool that is called only at the very end, and set interrupt_on={"publish_report": True} so the graph pauses for a human decision before anything is finalised. This is the safety property that makes the project defensible, and it is cheap precisely because the framework already implements interrupts.
Step 4Checkpoint / resume test
Kill the process mid-run and rerun with the same thread_id. Confirm it resumes from the last committed step rather than restarting — and confirm what happens to the step that was in flight when it died, which is the part worth actually observing.
Step 5Postgres checkpointer
Swap SQLite for langgraph-checkpoint-postgres. Same API surface, a connection-string change, and concurrent runs stop contending on a single file.

Running it today

The scaffold installs and constructs cleanly. What it cannot yet do is complete a real research run, because steps 1 and 2 above are the tools it would need.

What the architecture already buys

An architecture you can read in one screen

The topology is a constructor call. A reviewer can see every role, skill, memory source and interrupt without opening a second file.

Context isolation by construction

Each subagent gets its own window and its own tool scope, so a large document can never leak into a role that had no business reading it.

Methodology a human can edit

DCF conventions and filing red flags live in reviewable SKILL.md files, not buried in a prompt string.

Remaining work is configuration

Five known parameter changes, no re-architecture. That is the whole reason for having refused to write an orchestrator.

What I would want challenged

  • Do the four role descriptions actually route well? Untestable until the tools are real. If the lead agent routes a transcript question to the filings analyst, the fix is a description rewrite, not a code change — but I want the evidence before I claim it works.
  • Is a sandbox per run affordable? Spinning up an execution backend for a single DCF may be heavier than the modelling role justifies. Worth measuring before committing.
  • Is one approval gate enough? A single gate at publish is the minimum defensible design. A more conservative version would also gate anything that spends money or touches an external system.
